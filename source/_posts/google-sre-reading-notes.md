这篇笔记记录我阅读 [《Site Reliability Engineering》](https://sre.google/sre-book/table-of-contents/) 时，对 SRE 原则和实践的理解。每个主题尽量回答三个问题：

- **Why：为什么需要它？** 先理解生产环境中遇到了什么问题。
- **What：它是什么？** 明确概念、目标和边界。
- **How：怎么做？** 把原则落实到工程和日常工作中。

下面按学习主题整理，记忆点是个人理解与归纳，文末保留自测题，方便回顾。

## SRE 的整体视角

### SRE 关注哪些工作？

SRE 用软件工程的方法管理服务可靠性，在产品迭代速度、稳定性和成本之间做出取舍。阅读过程中，我先记住了几个主要工作领域：

1. **服务水平管理**：根据用户需求定义 SLI 和 SLO，围绕明确的可靠性目标开展工程工作。
2. **监控**：通过告警、工单和日志，让运行状态能够推动行动。
3. **应急响应**：提前准备工具和操作文档，减少故障影响，缩短恢复时间。
4. **变更管理**：逐步灰度，迅速、准确地发现问题，并能够安全回滚。
5. **需求预测与容量规划**：合理预测增长，定期测试容量和系统极限。

理解可靠性时，也要区分几个常见时间指标：MTTF 是平均失效前时间，MTBF 是平均故障间隔时间；MTTR 在这里指平均恢复时间。团队使用这些指标时，需要明确起止点和统计口径。

### 从 SRE 的视角看 Google 生产环境

这一部分帮助我建立生产环境的整体图景，主要用作后续章节的背景。

**硬件组织**可以按机器、机架、机架排、集群、数据中心建筑和园区来理解。书中还特意区分了 Machine 与 Server：前者指机器，后者指提供服务的软件。这里的层级来自 Google 的环境，不能直接套成所有云平台的 AZ、Region 层级。参见[原书的生产环境介绍](https://sre.google/sre-book/production-environment/)。

**请求路径**可以用一个简化示意帮助记忆：

```text
用户 → DNS / 全局流量调度 → 负载均衡 → 前端 / Proxy → RPC 服务 → 存储
```

沿着这条路径，分别考虑：流量进入哪个数据中心、请求交给哪个实例、依赖怎样被调用、状态保存在哪里。具体系统可以组合不同机制，DNS、L4 和 L7 负载均衡也有各自的职责。

### SRE 原则的主线

**记忆点：安全地提高产品迭代速度，需要把可靠性目标、运行反馈和工程改进联系起来。**

- **风险与目标**：风险评估 → SLO → 错误预算。
- **运行与反馈**：监控 → 发现偏差 → 干预和改进。
- **持续演进**：消除 Toil、推进自动化、完善发布工程。
- **贯穿原则**：保持简单。

## SRE 的原则

### 拥抱风险

**记忆点：管理服务可靠性，很大程度上就是管理风险；可靠性本身也有成本。**

1. **Why：为什么需要管理风险？** 故障会伤害用户，但过度追求可靠性也会增加成本、拖慢迭代。开发和 SRE 如果缺少共同目标，也容易对变更风险产生分歧。
2. **What：希望达到什么状态？** 根据用户和业务需求，结合成本，确定“足够可靠”的程度，并用 SLO 明确表达。
3. **How：怎样管理？** 围绕 SLO 安排测试、冗余、容量和发布节奏，并用错误预算协调可靠性投入与产品迭代。

例如，按请求成功比例定义的 SLO 为 99.9% 时，在约定窗口和统计口径下，允许的不合格请求比例就是 0.1%。错误预算关注的是这部分余量怎样被消耗，以及消耗速度是否需要改变工程决策。

### 服务水平目标：SLI、SLO、SLA

**记忆点：先知道用户真正关心什么、怎样衡量，才能有效管理服务。**

1. **Why：为什么需要明确服务水平？** 让团队对服务是否健康、哪些问题值得优先处理形成共同判断。
2. **What：这三个概念分别是什么？**

    | 概念 | 解决的问题 | 例子 |
    | --- | --- | --- |
    | **SLI：服务水平指标** | 实际服务水平怎样衡量？ | 合格请求中的成功比例、请求延迟分布 |
    | **SLO：服务水平目标** | 希望指标达到什么水平？ | 在约定的 30 天窗口内，请求成功比例至少为 99.9% |
    | **SLA：服务水平协议** | 对用户做出什么承诺，未达标有什么后果？ | 可用性低于约定目标时，按协议提供服务抵扣 |

3. **How：怎样制定和使用？** 先选择与用户体验相关的少量指标，明确采集位置、统计窗口、聚合方式和排除条件；再设定合理目标，并根据偏差采取行动。SLA 的制定还需要业务和法务参与。

内部 SLO 通常应比对外承诺更严格，给发现和处理问题留出余量。比较时要说清楚方向：可用性目标越高越严格，延迟上限越低越严格。定义与目标留余量的原则参见[原书的服务水平目标章节](https://sre.google/sre-book/service-level-objectives/)。

### 消除 Toil：避免重复的手动运维

**记忆点：服务规模增长时，重复运维工作不能无限挤占工程改进时间。**

1. **Why：为什么需要消除 Toil？** 如果重复操作随服务规模同步增长，团队就会越来越忙，却没有时间消除问题。
2. **What：Toil 是什么？** 它通常具有这些特征：需要人工操作、反复发生、可以自动化、由事件驱动而被动处理、不产生持久改进，并且随服务规模线性增长。
3. **How：怎样减少？** 留出软件工程和系统工程时间，识别高频、耗时的重复操作，通过工具、流程和系统设计形成持久改进。

### 分布式系统的监控

**记忆点：需要立即响应的告警，应指向真实的服务症状或即将发生的问题。**

1. **Why：为什么需要监控？** 分析趋势、触发告警、比较版本和实验效果、回顾问题，以及构建仪表盘。
2. **What：监控哪些内容？** 白盒监控观察系统内部暴露的指标和状态；黑盒监控从用户视角验证外部行为。服务监控可以先围绕四个黄金信号展开：

    | 黄金信号 | 回答的问题 | 例子 |
    | --- | --- | --- |
    | **延迟 Latency** | 请求处理有多慢？ | p50、p99，成功与失败请求的延迟 |
    | **流量 Traffic** | 系统承受多少需求？ | QPS、bps、CPS、并发会话数 |
    | **错误 Errors** | 有多少请求没有得到正确结果？ | 错误率、超时比例、内容错误 |
    | **饱和度 Saturation** | 系统距离资源极限还有多远？ | CPU 利用率、队列积压、连接池耗尽、内存余量 |

3. **How：怎样设置？** 关注尾延迟，选择合适的测量与聚合粒度，避免平均值掩盖短时尖峰，并让监控规则保持简单。

其中，饱和度要结合系统瓶颈判断。CPU、内存使用率可以作为线索，但还需要看排队和剩余容量；一些系统在利用率达到 100% 之前就已经明显退化。参见[原书的四个黄金信号](https://sre.google/sre-book/monitoring-distributed-systems/#xref_monitoring_golden-signals)。

### 自动化的价值

**记忆点：自动化能够提高一致性，把经过验证的操作能力沉淀到系统中。**

1. **Why：为什么需要自动化？** 提高一致性，形成共享平台，更快地修复问题和执行操作，并节省人工时间。
2. **What：自动化是什么？** 用软件执行和协调原本由人完成的操作，例如部署、配置、扩缩容和故障恢复。
3. **How：怎样推进？** 从明确、可重复的操作开始，逐步扩大自动化范围，同时明确失败处理和人工接管方式。

### 发布工程

**记忆点：构建并交付软件，需要一套一致、可重复的工程流程。**

1. **Why：为什么需要发布工程？** 让软件从研发到上线的过程受到规范控制，减少环境差异和手动操作带来的不确定性。
2. **What：发布工程包括什么？** 发布工程师与开发、SRE 一起定义软件交付所需的步骤：源代码管理、构建规则、测试、打包、部署和配置管理。
3. **How：怎样做？** 提供自助服务，支持高效发布；通过密闭构建控制输入和依赖，并让策略和流程能够被一致执行。

### 简洁性

**记忆点：系统越容易理解和预测，越有利于维护可靠性。**

1. **Why：为什么需要简洁性？** 复杂性增加理解、测试、变更和故障定位的难度。
2. **What：什么是简洁性？** 在满足业务需求的前提下，让代码、模块、接口和运行方式尽量清晰。
3. **How：怎样保护简洁性？** 删除不再需要的代码和功能，保持 API 精简，划分清楚模块边界，也让发布过程保持简单。

删除代码的价值在于减少不必要的复杂性，而不能仅用代码行数评价设计。

## SRE 的实践

### 基于时间序列数据的实用告警

**记忆点：监控的核心，是把运行状态转化为可以采取行动的依据。**

1. **Why：为什么需要监控告警系统？** 把大量实例的运行情况转化为可查询、可比较、可采取行动的信息，帮助发现问题、定位原因，同时控制监控自身的维护成本。
2. **What：它处理什么数据？** 数值的含义，例如 Gauge、Counter；数值的归属，即指标名与标签集合；数值的历史，即时间戳与对应的值。
3. **How：数据怎样推动行动？** 埋点产生指标 → 暴露并采集 → 时间序列数据库存储 → 查询与计算 → 告警规则 → 人员行动。

```text
运行状态 → 数值 → 判断 → 行动
```

### On-Call：值班

**记忆点：值班需要及时响应，也需要能够长期持续。**

1. **Why：为什么需要值班？** 当生产问题需要人工判断和处理时，确保有人及时响应，同时避免持续救火耗尽团队的工程能力。
2. **What：值班是什么？** 在约定轮值期间承担生产问题的第一响应职责：接收告警、判断影响、推动恢复，并在需要时寻求支援或升级处理。
3. **How：怎样让值班有效？** 均衡轮班和运行负荷，关注告警质量、事件数量、交接和补偿，并持续改进造成重复打扰的问题。

### 应急响应

**记忆点：故障无法完全避免，应急能力需要提前准备。**

1. **Why：为什么需要应急响应？** 紧急情况下可能同时出现工具失效、信息不足和人员紧张。提前准备可以降低影响，帮助尽快恢复服务。
2. **What：应急响应是什么？** 一套应对突发故障的能力，包括事前准备、故障中的止损与恢复，以及事后的改进。
3. **How：怎样做好？** 事前准备工具、权限、文档并演练；事中判断影响、控制变更、止损和恢复；事后记录事实并落实改进。

### 事件管理

**记忆点：多人处理故障时，需要清晰的职责与共享的信息。**

1. **Why：为什么需要事件管理？** 多人、多团队参与时，容易出现重复排查、操作冲突、信息断层，以及技术负责人被沟通事务拖住的问题。
2. **What：事件管理是什么？** 故障处理期间的组织协作机制，明确谁指挥、谁操作、谁沟通、谁保障后续工作，以及如何共享信息。
3. **How：怎样管理？** 及早宣布事件，建立统一沟通渠道，明确职责、协调操作、共享状态，持续调整响应规模，并做好交接。

### 事后文化：从失败中学习

**记忆点：复盘需要形成可以减少故障复发概率或影响的改进。**

1. **Why：为什么需要复盘？** 服务恢复后，如果没有系统学习和改进，同类故障就可能反复发生。
2. **What：复盘是什么？** 一份可以审阅和共享的书面记录：发生了什么、造成什么影响、如何处理、有哪些促成原因，以及后续怎样改进。
3. **How：怎样做好？** 提前确定复盘条件 → 还原事实 → 无责分析原因 → 制定改进措施 → 审阅与分享 → 落实改进。

### 故障跟踪

**记忆点：有已知基线，并且能够跟踪变化，才能判断可靠性是否真的提高。**

1. **Why：为什么需要持续跟踪？** 单次故障处理完后，还需要看长期趋势：哪些问题反复发生，哪些服务最消耗值班精力，改进有没有效果。
2. **What：跟踪哪些信息？** 事件时间、影响、处理过程、原因分类、采取的操作，以及误报等信息。
3. **How：怎样组织？**
    - **归并**：一次网络故障可能触发几十条服务告警，要把它们关联到同一个事件，分别统计告警数和事件数。
    - **记录与分类**：补充 `cause:network`、`action:rollback` 等标签与注释。
    - **横向和长期分析**：比较服务、团队与时间段，识别共同的基础设施问题，并验证改进效果。

### 可靠性测试

**记忆点：用测试减少变更的不确定性，也验证系统失效和恢复时的行为。**

1. **Why：为什么需要测试？** 尽早发现问题，减少变更带来的风险，并验证系统能否按预期运行和恢复。
2. **What：可以测试哪些方面？** 下面这些类型从不同角度检查系统，彼此可以交叉：

    | 测试类型 | 主要检查什么？ |
    | --- | --- |
    | 单元测试 | 函数或模块的行为是否正确 |
    | 集成测试 | 多个组件之间的交互是否正确 |
    | 系统测试 | 完整系统是否满足预期行为 |
    | 冒烟测试 | 最基本的关键功能是否可用 |
    | 性能与负载测试 | 在不同压力下，吞吐、延迟和资源消耗怎样变化 |
    | 回归测试 | 变更是否破坏已有行为 |
    | 模糊测试 | 异常、边界或生成的输入是否触发缺陷 |
    | 故障注入测试 | 依赖失效、网络异常等情况下，系统怎样表现 |
    | 灾难恢复测试 | 故障后能否恢复数据与服务 |
    | 稳定性测试 | 持续运行一段时间后是否仍然正常 |
    | 兼容性测试 | 不同版本或配置能否按预期协同工作 |
    | 黑盒探测 | 从外部调用方视角看，服务是否可用且结果正确 |

3. **How：怎样落到流程中？** 按风险确定优先级，设计有明确判定条件的用例，自动化执行，并验证真实部署。生产变更还需要结合金丝雀发布和监控，逐步扩大影响范围。

### SRE 中的软件工程

**记忆点：把生产问题转化为有明确用户、能够持续维护的软件产品。**

1. **Why：为什么 SRE 需要开展软件工程？** 通过软件和自动化减少重复劳动、提高可靠性，让服务规模增长时，所需人力不必同比增长。SRE 对生产复杂性的直接经验，也有助于选对工具要解决的问题。
2. **What：具体做什么？** 围绕生产需求开发内部软件，例如发布机制、监控系统和开发工具，并提供需求、设计、测试、发布和持续维护机制。
3. **How：怎样开展？** 选对问题并明确需求；先做可用版本，再持续迭代；把推广和用户支持作为开发的一部分；按正式软件产品的标准保证质量，并保持与生产环境的联系。

### 前端负载均衡

**记忆点：入口流量分配需要同时考虑可用性、延迟、吞吐和资源利用率。**

1. **Why：为什么需要前端负载均衡？** 单机存在容量限制和单点风险，单个数据中心也无法兼顾全球用户的访问体验。
2. **What：它是什么？** 在服务入口，根据用户位置、业务需求、容量和健康状态，将外部流量分配到合适的数据中心及服务实例。
3. **How：怎样分配？** 可以拆成三个问题：
    - **选择哪个入口或数据中心？** DNS 可以返回合适的 A/AAAA 地址；选择时要考虑用户位置、网络延迟、容量、健康状态，以及递归解析器和缓存带来的限制。
    - **选择 VIP 背后的哪台实例？** 根据负载或哈希选择后端，并配合连接跟踪保持连接亲和性；后端集合变化时，尽量减少对已有连接的影响。
    - **怎样把包送到实例？** 可以采用 NAT、修改二层目标 MAC、GRE 等隧道封装。具体方案要考虑回包路径、连接状态、二层可达性、封装开销和 MTU。

### 数据中心负载均衡

**记忆点：调用方需要从一组后端中，为请求选择合适的处理者。**

1. **Why：为什么需要负载均衡？** 避免部分实例先过载、其他容量却闲置，同时控制连接成本，支持安全上下线。
2. **What：它是什么？** 数据中心内部，调用方怎样选择并使用一组后端处理请求。
3. **How：怎样做？** 通过健康与生命周期管理确定接流量资格；通过子集化控制连接规模；通过请求调度策略按实际能力分摊负载。

当调用方很多、后端很多、连接需要长期保持时，连接数量和维护成本都需要单独考虑，TLS 连接还涉及握手等开销。

### 处理过载

**记忆点：超过容量时，系统仍应稳定处理自己承受得住的那部分请求。**

1. **Why：为什么需要过载保护？** 资源有限，流量突增、请求成本变化、负载分配不均都可能导致过载。如果任由请求堆积和重试放大，可能出现延迟上升、资源耗尽和进程崩溃，进而引发级联故障。
2. **What：过载保护是什么？** 根据可用资源、客户配额和请求重要性控制接受的工作量；必要时降低服务质量、拒绝部分请求，并约束客户端继续发送和重试的行为。
3. **How：怎样实现？**
    - **判断过载**：结合请求量、CPU、内存、队列和并发数，识别实际瓶颈。
    - **资源公平**：按客户设置配额，避免一个客户挤占其他客户的资源。
    - **保留重要请求**：资源不足时，按请求重要性决定接收和丢弃顺序。
    - **减少工作量**：通过降级、连接池和批处理，降低请求与连接维护成本。
    - **提前拒绝**：如果服务端拒绝请求本身也很昂贵，客户端可以根据反馈在本地限制发送。
    - **约束重试**：只对适合重试的错误进行受控重试；大面积过载时，继续重试可能让恢复更困难。

客户端限流控制发送速率或工作量；熔断则根据依赖的健康状态暂时阻断调用。两者可以配合使用。

### 应对级联故障

**记忆点：要知道系统的临界点在哪里，以及越过临界点之后会怎样。**

1. **Why：为什么需要防范级联故障？** 组件之间相互依赖、共享资源，局部故障可能增加其他组件的负载，或者降低整体处理能力。
2. **What：什么是级联故障？** 一种典型的正反馈过程是：

    ```text
    部分实例失效 → 可用容量减少 → 剩余实例承担更多负载
         ↑                                  ↓
         └──────────── 更多实例失效 ─────────┘
    ```

3. **How：怎样防止和应对？** 隔离故障域，限制队列与并发数，设置处理时间上限，控制重试；测试超过极限后的行为，也测试恢复过程，检查冷缓存和批量重启是否带来额外负载。发生故障时，先通过限流、降级、熔断或有效扩容让系统稳定下来，再继续排查。

### 管理关键状态：通过分布式共识实现可靠性

**记忆点：识别哪些关键状态需要共识，理解仅靠心跳判断存活时的边界。**

1. **Why：为什么需要分布式共识？** 服务和状态复制到多个节点后，节点仍会崩溃，网络仍会延迟、丢包和分区。多个节点可能因此对“谁是主节点”“配置是什么”等关键问题产生不同认知。
2. **What：分布式共识是什么？** 让一组通过不可靠网络通信的进程，按照明确协议对决定达成一致。
3. **How：怎样使用？** 识别必须一致的关键状态；优先使用成熟的 etcd、ZooKeeper 等系统；配置足够副本并分散故障域；结合领导者、批处理、流水线和分片等方式平衡性能；部署时考虑副本位置、客户端距离、跨地域延迟和故障范围；运行时观察领导者与提交进展。

### 使用 Cron 进行分布式周期调度

**记忆点：调度器的高可用与作业启动的正确性，需要分别解决。**

1. **Why：为什么分布式调度难做？** 单机 Cron 故障可能导致漏启动，重新调度又可能造成延迟和状态丢失。增加备用调度器后，还必须防止接管时重复启动。
2. **What：分布式周期调度是什么？** 多副本调度服务保存作业配置、计划启动时间和启动状态；由 Leader 请求执行系统启动作业，其他副本同步状态，并在故障后接管。
3. **How：怎样实现？**
    - **谁接管？** 多副本热备，通过共识选择 Leader。
    - **怎样区分轮次？** 使用“作业标识＋计划启动时间”标识一次计划启动。
    - **启动到一半崩溃怎么办？** 新 Leader 检查未完成记录；依靠外部操作的幂等性或状态查询，补齐尚未完成的部分。
    - **还要检查什么？** 防止新旧 Leader 同时操作，恢复持久状态，并处理大量作业集中启动时的容量问题。

共识能帮助管理调度状态；外部执行已经发生到哪一步、重复请求是否安全，也必须有明确机制。

### 数据处理流水线

**记忆点：任务状态与执行进程分离，计算可以重做，结果提交必须受控。**

1. **Why：为什么需要 Workflow 这样的系统？** 随着数据量和时效要求提高，以“定时启动、整轮完成”为单位的流水线可能出现调度积压、长尾阻塞、失败后大量重算，以及共享资源冲击。
2. **What：书中这套 Workflow 系统是什么？** 管理任务如何沿流水线推进的协调系统，主要角色包括：

    | 角色 | 职责 |
    | --- | --- |
    | **Task Master：任务主控** | 保存任务状态、租约、配置版本和数据引用，检查并提交状态变更 |
    | **Worker：工作进程** | 领取任务、读取数据、执行计算、写出结果，再向主控提交 |
    | **Controller：控制器，可选** | 管理扩缩容、快照、暂停、回滚和故障转移等操作 |

3. **How：怎样保证可靠性和正确性？** 将任务状态与执行进程分离，允许失败后重新计算，严格控制结果提交，并为跨集群恢复保留明确依据。

### 数据完整性

**记忆点：恢复能力需要通过持续演练来证明。**

1. **Why：为什么需要数据完整性保障？** 程序错误、误操作和基础设施故障都可能造成数据丢失或损坏，多副本也可能传播错误。
2. **What：希望达到什么状态？** 保证数据正确、完整，并能在业务允许的时间和数据损失范围内恢复。
3. **How：怎样做？** 通过软删除、分层备份和故障隔离保留恢复机会；通过完整性检查尽早发现问题；持续执行端到端恢复演练，验证数据与应用都能恢复，并测量耗时和数据损失范围。

### 大规模产品的可靠上线

**记忆点：开发完成、测试通过之后，还需要验证上线准备与故障处置能力。**

1. **Why：为什么需要专门关注上线？** 上线涉及开发、SRE、依赖服务等多个团队，容易遗漏容量准备、配置顺序、职责和协作方式。
2. **What：什么是可靠上线？** 上线前，服务和依赖已经准备好；上线中，影响范围逐步扩大，效果能够被观察；出现问题时，能够及时停止、关闭功能或回滚。各团队知道自己负责什么，以及怎样配合。
3. **How：怎样落实？** 上线前使用检查清单并制定实施计划；上线中逐步开放、验证指标，明确继续或停止的条件；上线后学习并改进清单与流程。

## 回顾与自测

### SLI、SLO、SLA 分别解决什么问题？

- **SLI：观测指标**，说明怎样衡量实际服务水平。
- **SLO：目标**，说明指标在什么窗口、口径下应达到什么水平。
- **SLA：协议与承诺**，说明约定目标，以及未达标的后果。

### 四个黄金信号是什么？

**延迟、流量、错误、饱和度。** 记住 p99、QPS、错误率、CPU 使用率等例子之后，还要能解释它们分别反映什么，以及是否覆盖了当前系统的瓶颈。

### 自动化的价值是什么？

提高一致性，减少重复劳动，加快操作和恢复，把经验沉淀成可重复执行的能力。实现时也要控制自动化系统自身的复杂性。

### 我怎样理解 SRE 的工作？

以用户需要的可靠性为目标，通过工程方法持续改进系统，在迭代速度、稳定性与成本之间取得平衡。

### 怎样保护过载中的系统，避免级联故障？

限流、降级、熔断，限制队列与并发，限制处理时间，并控制重试。需要同时验证失效过程和恢复过程，避免恢复操作带来新的冲击。

### 重试要考虑哪些问题？

- 使用带随机抖动的指数退避。
- 限制每个请求的重试次数，并考虑整个进程的重试预算。
- 选择合适的一层负责重试，避免多层重试相乘放大请求。
- 区分错误类型和状态码，只重试可能恢复且可以安全重试的操作。
- 检查操作的幂等性，以及剩余时间是否允许再次尝试。
- 过载时结合降级或停止重试，避免增加系统压力。

### 数据有三个副本，备份每天成功，为什么误删后仍可能无法恢复？

误删可能已经传播到全部副本；备份也可能包含错误、缺少必要数据，或者虽然保存成功，恢复过程却无法正确完成、耗时过长。

证明恢复能力，需要实际执行端到端恢复演练，检查恢复后的数据与应用是否正确可用，并测量恢复耗时和数据损失范围。

### 周期调度的 Leader 执行到一半崩溃怎么办？

接管者需要知道执行状态，或者能够安全地重试。为每轮启动提供明确标识，持久记录进度，并让外部操作支持幂等或状态查询。

### 新功能通过功能和负载测试，上线前还要确认什么？

使用检查清单确认对已有服务和上下游的影响、容量与依赖准备、负责人、灰度步骤、实施计划、观察指标、停止条件和回滚方案。每一步扩大影响范围前，都要根据实际运行结果判断是否继续。
